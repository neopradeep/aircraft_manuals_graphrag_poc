# Aircraft Maintenance Manuals + Knowledge Graph (GraphRAG proof of concept)....WIP

An experiment: **can a knowledge graph answer aircraft parts questions more reliably than plain AI search?**

> All data here is **synthetic and fictional**, generated by a script. It contains no real airline, manufacturer, or manual content, and it is **not for real maintenance use**. It is a learning project and a starting point.

---

## Part 1: The idea in plain language

### The problem
Airlines keep thousands of pages of maintenance manuals. A mechanic needs quick, exactly-right answers to questions like:

- "Part X isn't in stock. What else can I install instead?"
- "Is that substitute allowed on a 737-800, or only on a MAX?"
- "Can I swap it both ways, or only in one direction?"
- "Does the vendor manual agree with the parts catalog?"

Getting these wrong is not a small mistake. The answer must be right, and you must be able to point to the page it came from.

### Why plain AI search struggles
The common approach ("vector search") chops manuals into pieces, finds the pieces that *sound* most similar to the question, and has an AI summarize them. That works for "what does this section say?" It struggles when the answer depends on **relationships** spread across pages:

- Part A replaces part B, **but B cannot replace A** (one-way).
- The swap is allowed **only after a service bulletin** is applied.
- The swap works **only on certain aircraft variants**.
- Two documents, or two revisions of one document, **disagree**.

Similar-sounding text does not tell you which direction a substitution goes.

### What we tried instead
We turn the manuals into a **graph**: parts, assemblies, aircraft variants and procedures are dots, and the real-world relationships ("can replace", "is installed on", "is required by this task") are the lines between them. Every line remembers which document and revision it came from, so answers can cite their source. We keep the original text too, so we can still search by meaning.

Then we ask the same 61 test questions three ways and **score each one**:

| Method | How it finds the answer |
|---|---|
| **Vector** (baseline) | Finds similar-sounding text only |
| **Graph** | Looks up the exact part and follows relationships |
| **Hybrid** | Both: meaning search to get started, graph to follow the facts |

The scorecard (accuracy, whether the right source was cited, and speed) is the result of the experiment.

### What you get from this project
A realistic fake manual set, a graph model, a loader, three retrievers, and a scorecard. You can run it on a laptop in about 15 minutes, then poke at the graph in Neo4j Browser.

### Honest limits
- The data is synthetic. It looks like real manuals but won't have every quirk of real ones.
- An AI model reads the "interchangeable with..." statements and turns them into graph links. It can make mistakes, and the scorecard will show where.
- The corpus is small (69 documents). Treat results as directional, not as a benchmark.

```

src/retrieve.py                The three retrievers (vector / graph / hybrid) + answer generation
src/evaluate.py                Runs every question through every retriever and scores them

results/                       Scorecards written by each evaluation run (git-ignored, created on first `make eval`)

```

### The test data in numbers
628 parts across 61 assemblies, for two aircraft families (737-style and A320-style, each with three variants). 140 interchangeability records. Built-in traps: one-way substitutions, service-bulletin conditions, variant-limited swaps, 3 places where a vendor manual contradicts the parts catalog, and 4 statements that changed between catalog revisions 14 and 15.

### The 61 questions
Interchangeability (14), one-way supersession (6), effectivity by variant (10), assembly/ATA lookup (6), procedure lookup (8), multi-step alternates (6), vendor-vs-catalog conflicts (3), revision changes (4), and "which manuals mention this part" (4).

## Part 3: How it works (technical)

### Pipeline
```
HTML manuals -> parse (structure-aware chunks) -> embed chunks
                         \-> extract part/variant/procedure facts (deterministic, from tables)
                         \-> interchangeability notes -> LLM -> typed relations (JSON)
              -> load into Neo4j (graph + vector index)
question -> retriever (vector | graph | hybrid) -> LLM answers from retrieved context only -> judged vs. expected answer
```

### Chunking
Chunks follow the document structure, not a fixed character count. A parts catalog item with its alternates and notes stays together; a procedure is split by heading; a vendor manual by numbered section. Each chunk is prefixed with its document, revision, ATA section, and figure so it makes sense when retrieved alone. Part numbers found in a chunk become `MENTIONS` links.

### Graph model
**Text layer:** `(Document)<-[:IN_DOCUMENT]-(Section)<-[:IN_SECTION]-(Chunk {embedding})-[:MENTIONS]->(Part)`

**Domain layer:**
- `(Part)-[:COMPONENT_OF {item, qty}]->(Assembly)`
- `(Part)-[:EFFECTIVE_ON]->(Variant)`
- `(Part)-[:CAN_REPLACE | CANNOT_REPLACE | SUPERSEDES {doc, revision, source_type, condition, only_variants, statement}]->(Part)`
- `(Procedure)-[:COVERS]->(Assembly)`, `(Procedure)-[:REQUIRES_PART]->(Part)`

Replacement edges are directional and carry their provenance, so conflicts and revisions can be shown rather than hidden. Indexes: a vector index on chunk embeddings and fulltext indexes on assembly and procedure names.

### Retrievers
- **vector**: embed the question, take the top 6 chunks, answer from them.
- **graph**: find part numbers in the question, query the part's assembly, effectivity, replacement edges and procedures from Neo4j.
- **hybrid**: graph facts for named parts, plus parts reached from the best-matching chunks, plus supporting passages.

The answer prompt tells the model to use only the supplied context, respect effectivity and direction, flag conflicts (preferring the latest catalog revision), and cite document names.

### Scoring
For each question and retriever: an LLM judge compares the answer to the expected answer (direction, conditions, variant limits, and conflict flags must match), plus **source recall** (did it cite the documents it should have?) and latency. The summary table is written to `results/summary-<timestamp>.md`.

## Part 4: Run it yourself

### You need
Python 3.10+, a local **Neo4j** (a version with vector index support, 5.18 or newer), and an API key for an **OpenAI-compatible** AI provider (OpenAI or Fireworks both work).

### Steps
```bash
git clone <this-repo-url> && cd aircraft_manuals_graphrag_poc
make setup                      # creates .venv and installs dependencies (once)
cp .env.example .env            # then edit .env (see below). Never commit it.
make models F=zzz               # checks your AI key/models work and shows timing
make dry-run                    # parses the manuals only: should print docs=69 chunks=752 ...
make ingest                     # builds the graph  (WIPES the target Neo4j database)
make ask M=hybrid Q="..."       # ask one question
make eval                       # run all 61 questions x 3 retrievers, write the scorecard
```
For a quick trial: `./.venv/bin/python -m src.evaluate --limit 8`.

### Configure `.env`
```
NEO4J_URI=neo4j://127.0.0.1:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=...
NEO4J_DATABASE=neo4j            # use a throwaway database; ingest deletes everything in it

# OpenAI:
OPENAI_API_KEY=...
# or any OpenAI-compatible provider, e.g. Fireworks:
LLM_BASE_URL=https://api.fireworks.ai/inference/v1
LLM_API_KEY=...
LLM_CHAT_MODEL=<a fast, non-"reasoning" chat model that supports JSON mode>
LLM_EMBED_MODEL=<an embedding model>
EMBED_DIM=<that embedding model's output size>
```
`make models` prints the real embedding size and warns if it differs from `EMBED_DIM`. Use one embedding model per database; if you switch, re-run `make ingest`.

### Look at the graph
In Neo4j Browser, pick a part that has alternates (see `ground_truth/interchange.json`):
```cypher
MATCH (p:Part {pn:"60-30926-23"})-[r:CAN_REPLACE|CANNOT_REPLACE|SUPERSEDES]-(q) RETURN p, r, q
```
Only about 30% of parts have alternates, so an empty result for a random part is normal.

### Regenerate or change the data
`python generator/generate_corpus.py --seed 7` writes a new corpus, truth files, and question set. Then `make ingest` again.

## Part 5: Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| `externally-managed-environment` error from pip | Use the project's venv: `make setup`, or call `./.venv/bin/python -m pip ...` |
| Ingest is very slow at "extracting" | The chat model is slow (often a reasoning model). Pick a faster one; check with `make models`. Results are cached, so re-runs skip finished work |
| Embedding dimension mismatch / index error | `EMBED_DIM` doesn't match the embedding model. Fix it, then `make ingest` (it rebuilds the index) |
| `structured relations` far below 216 | The model isn't following the JSON format. Try another chat model |
| Query returns nothing for a part | The part may simply have no alternates; check `ground_truth/interchange.json` |
| `Set NEO4J_PASSWORD` / `Set LLM_API_KEY` | `.env` missing or not in the project folder |
